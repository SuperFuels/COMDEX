# AION General Apprenticeship Executor

## Promotion

The internally evaluated procedure
`procedure_general_apprenticeship_executor_v1` is promoted. It is the first
executor attached to the Autonomous General Apprentice kernel that carries a
learning contract through resource discovery, exercise invention, real
execution, criticism, transfer, restart retention and curriculum feedback.

The immutable mission was:

> Learn how to preserve service continuity when unfamiliar persisted state
> becomes empty or malformed, then transfer the verified method to a
> qualitatively different transactional application.

## End-to-end learning chain

```text
broad immutable objective
  -> discover public repository and tool authorities
  -> infer the missing state distinctions
  -> invent progressively harder exercises
  -> reproduce a natural historical failure
  -> construct a private candidate repair
  -> execute public counterexamples
  -> reveal held-out repository verification only after selection
  -> compare with the later human outcome
  -> abstract the verified method
  -> transfer it to a source-disjoint SQLite application
  -> reconstruct and retest without source replay
  -> register a reusable proposal-only executor contract
  -> return a verified receipt to the autonomous curriculum
```

## Natural repository authority

The executor used the historical COMDEX change
`9444c7c4d2539aaaab91e5e821b3a234f630eddf` and its parent
`15eb75a56594132e10e5785214fbad21b1c55ddb`. It operated on disposable local
Git clones of the parent snapshot. The natural change description and parent
source were available; the later human implementation was not exposed to the
proposal mechanism before candidate selection.

From the parent implementation AION inferred five relevant persistent-state
concepts: missing, valid, empty, malformed and quarantined. It then generated
six increasing exercises, culminating in two independently corrupted artifacts
whose evidence had to remain recoverable while disappearing from active
enumeration.

The original checkout failed the invented property. The private challenger
passed the public exercises, Python compilation and the withheld repository
test. Only then was the historical human outcome opened. The challenger was
accepted on behavioural equivalence---optional absence, empty-state handling
and quarantine---rather than source-code equality.

## Transfer and compounding improvement

The retained method was:

> validate, quarantine, preserve evidence, then return absence.

It was transferred from a file-backed Python repository into a fresh in-memory
SQLite application with active and quarantine tables. An identical cold method
search required three attempts: ignore invalid state, delete invalid state, and
finally quarantine while preserving evidence. The retained apprentice selected
the successful method on its first attempt, a 66.67\% reduction.

After state reconstruction, the same abstract method was applied to a renamed
telemetry-packet application with zero source replay and zero relearning. The
verified outcome was written back to the general apprentice as a retained
`transactional_data_integrity` receipt. This changed the curriculum generation
score from 0.0 after the failed first challenger to 1.0 after the corrected
challenger.

## Rejected attempt and metacognitive correction

The first challenger did not pass. Its security critic attributed an existing
explicit delete operation in the parent repository to the proposed repair.
That was an attribution error: the candidate itself introduced no deletion.
The critic was narrowed to audit the proposed delta while leaving the complete
candidate subject to executable behavioural tests. A separate SQLite execution
failure then exposed an unclosed seed transaction; the private experiment was
corrected by committing the seed state before beginning the intervention.

Neither failed attempt was promoted. Both remain part of the outcome history.
This is the intended learning pattern: diagnose the failing layer, revise the
private challenger, rerun independent authority and retain only the verified
result.

## Reusable executor contract

The successful procedure is now registered in persistent apprentice state as a
proposal-only executor. Its contract records the conditions under which it may
be proposed, the Python execution authority it may use, its verified
capabilities and its two transfer families. A verified outcome receipt is
required before an executor can be registered. Executor registration cannot
grant decision authority, introduce an unapproved authority or mutate the
owner's terminal mission.

## Claim boundary

This is a genuine complete apprenticeship loop, but it is one bounded mission.
The target historical file, generic corruption representation, exercise
semantics, security policy and verification harness remain engineered. The
transfer crosses repository recovery and transactional data integrity, not two
entirely unrelated intellectual subjects. Retention is process-separated, not
month-separated.

The next evidence requirement is repeated autonomous use of the executor model
across multiple unfamiliar objectives and authorities. Future curricula must
select or invent executor contracts, acquire missing tools, demonstrate
positive cross-subject transfer, and preserve competence over elapsed operation
without returning to one hand-authored workflow per lesson.
