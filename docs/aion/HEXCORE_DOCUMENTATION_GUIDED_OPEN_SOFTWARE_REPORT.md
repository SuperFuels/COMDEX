# AION HexCore Documentation-Guided Open Software Intelligence

**Date:** 31 July 2026

**Rejected escalation:** `procedure_source_grounded_software_memory_2750f049c98f`

## Objective

Rejoin AION's knowledge and software tracks. Given public repository
documentation, an issue and a source tree—but no repair menu, official patch or
target hint—AION must invent a repository ontology, ground document concepts in
actual source symbols, propose unrestricted exact replacements, describe
functional and adversarial security falsification tests, execute candidates in
fresh sandboxes and compete against an otherwise identical no-memory arm.

## Evaluation correction

The first paired execution used Python 3.14. Marshmallow failed before candidate
execution because that historical revision imports `distutils`, removed from
that interpreter. This run was invalid and did not authorize a decision. The
cohort was rerun under COMDEX's established Python 3.13 virtual environment.
This changed the measured control from 33.33% to 100%, demonstrating why
environment validation must precede capability interpretation.

## Architecture

```text
RFC / documentation / issue
        -> open concepts, relations and invariants
        -> exact quotation + document checksum verification
        -> proposed document-to-code bindings
        -> source-symbol confirmation
        -> persistent repository ontology
        -> unrestricted patch proposal
        -> functional + adversarial security test specifications
        -> static security scan
        -> fresh sandbox execution
        -> historical verification revealed after selection
        -> CAU promotion or rejection
```

Both experiment arms used the same GPT proposal model, issue, source tree,
localizer, tools, round budget, sandbox verifier and historical metadata. Only
the challenger received accumulated verified documentation memory.

## Security scanner correction

The first audit discovered that Python's `0o777` world-writable notation was
not matched by the existing `0777`-oriented rule. The scanner now recognizes
both forms. Six executable probes—dynamic execution, shell execution,
verification bypass, world-writable permissions, embedded secrets and security
bypass—are all rejected. Functional success cannot override this gate.

## Rejected source-grounded escalation

A second challenger added nine source-grounded test excerpts and six call-site
excerpts. It repaired Marshmallow and pydicom but failed pvlib, reducing success
to 66.67% and increasing attempts from five to ten. It was rejected. This shows
that indiscriminately adding code context can rotate proposal behavior away
from a valid numerical repair. Future routing must estimate whether each memory
item has positive expected value before exposing it to the patch proposer.

## Claim boundary

These are three public SWE-bench development issues with engineered executable
verifiers. Public-task contamination cannot be excluded. The model proposed
test specifications; the accepted repairs were evaluated by existing executable
tests, so AION has not yet invented and executed complete test programs. This
is documentation-grounded experimental repair with measured memory efficiency,
not independent software-engineering certification.

## Next stage

Build a governed semantic-memory router. It must choose among documentation
memory, source-grounded test contracts, prior failure experience or no-memory
fallback based only on training-side evidence. Promotion requires stable gains
over multiple seeds, at least five repositories and three languages, executable
self-invented tests that reject wrong patches, hidden verification and an
independent evaluator-owned cohort.
