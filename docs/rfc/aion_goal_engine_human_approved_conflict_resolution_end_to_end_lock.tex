\subsection{Purpose}

This lock proves that AION can surface a child-agent conflict, capture a human decision, and expose the approved resolution path in the Goal Engine preview bundle without automatically resolving the conflict or mutating live state.

The locked chain is:

\begin{verbatim}
child_agent_conflict_preview
  -> human decision
  -> human_approved_conflict_resolution_preview
  -> GoalEnginePreviewBundle
  -> Boardroom visibility surface
\end{verbatim}

\subsection{Safety Invariants}

The conflict-resolution preview MUST remain review-only.

It MUST NOT:

\begin{itemize}
  \item auto-resolve child-agent conflicts;
  \item execute child agents;
  \item mutate parent goals;
  \item mutate child goals;
  \item write to external systems;
  \item mutate business containers;
  \item grant permissions;
  \item bypass human review.
\end{itemize}

Canonical safety fields include:

\begin{verbatim}
dry_run_only = true
would_auto_resolve = false
would_execute = false
would_write_external = false
would_grant_permission = false
would_mutate_parent_goal = false
would_mutate_child_goal = false
\end{verbatim}

\subsection{Human Review Boundary}

A valid human-approved conflict-resolution preview requires:

\begin{itemize}
  \item a parent goal identifier;
  \item a conflict preview;
  \item conflict_detected = true;
  \item a human decision;
  \item a reviewer identifier.
\end{itemize}

If any of these are missing, the preview MUST remain blocked.

\subsection{Preview Bundle Visibility}

The Goal Engine preview bundle MUST preserve both the original conflict preview and the human-approved conflict-resolution preview.

The bundle MUST expose enough text and machine-readable payload for Boardroom surfaces to show:

\begin{itemize}
  \item the child-agent conflict;
  \item the recommended human-review path;
  \item the human decision;
  \item the reviewer;
  \item the approval gate;
  \item the safety flags;
  \item the fact that no automatic resolution occurred.
\end{itemize}

\subsection{Implementation Notes}

This lock does not create a live conflict resolver. It only locks the safe preview and review boundary.

The next runtime step, if needed, is a guarded approval-action flow that consumes this preview and creates a separately reviewed mutation proposal. That future step MUST remain distinct from this preview lock.
