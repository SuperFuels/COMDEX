\section{GPT-OSS 120B Adaptive Working-Set and Persistent-Output Breakthrough}
\label{sec:gptoss120b-adaptive-pool-20260910}

\subsection{Scope and claim boundary}

This section records a substantial performance result on the existing 18~GB
Apple M3 Pro and the 64~GB SD-backed AION warehouse.  It does not report a
smaller fallback model.  All transformer evaluations used the GPT-OSS 120B
Q4\_K\_M/MXFP4 checkpoint, its original attention and backbone tensors, and
original expert weights retrieved losslessly from the verified warehouse.

The first accelerated configuration below is a \emph{changed-model quality
track}: each layer's router may select only from a bounded resident pool of
original experts.  It is therefore not bit-exact unrestricted GPT-OSS 120B and
must not be described as such.  A later protected-core/exception-halo variant
restores unrestricted routing and is explicitly compared bit-for-bit with the
exact reference.  Neither track has reached 30--50 tokens/s.

\subsection{Exact route-cartridge falsification}

An exact 6--10~GiB route cartridge was first tested using held-out route demand.
The predeclared minimum was 90\% coverage for every family.  Same-family
coverage ranged from 30.2083\% to 66.1111\%, while cross-family minimum
coverage stayed below 47\%.  Increasing capacity did not add unobserved future
experts.  The exact cartridge was therefore stopped rather than integrated.
Its canonical SHA-256 is
\texttt{295232993424e95c44cac975933210dd5bbc3883dbc39cee30099ec21711df4c}.

Uniform pools of 16 and 20 experts per layer were then tested in the separately
labelled quality track.  Both removed continuation-time SD faults, but both
damaged the Harmony response structure.  These variants were retained as
non-promoted failures.  This motivated a variable-width pool that protects all
experts required by the complete seven-token prompt prefix before allocating
the remaining capacity by observed frequency per byte.

\subsection{Adaptive 10~GiB working set}

The resulting pool contains 810 layer/expert addresses and
10,735,545,600 resident raw bytes.  Individual layers retain between 15 and 46
experts.  It includes all 499 distinct layer/expert addresses observed in the
seven-token Harmony prefix.  Activation required approximately 114 seconds of
one-time SD retrieval and verification.  Once resident, every measured
continuation pass recorded zero expert faults, zero evictions, and zero
compressed SD bytes read.  This 10~GiB quality-track pool is intentionally
separate from the 1--3~GiB exact streaming-cache ceiling.

The 24-position test comprised seven teacher-forced prompt positions followed
by 17 genuinely autoregressive positions with KV history, changing hidden
state, and changing routes.  The initial persistent-output candidate achieved
2.8363 and 4.3807 tokens/s, compared with 0.07679 and 0.07754 tokens/s for the
matched unrestricted control.  The corresponding paired speedups were
36.934$\times$ and 56.496$\times$.

\subsection{Persistent vocabulary output}

Profiling showed that every position recreated a process and reread a roughly
615~MB vocabulary projection.  A bounded persistent native output arena was
therefore added.  It holds a read-only memory mapping of the original Q8 output
weight and reuses a 768~MiB GGML arena.  On an unrestricted BOS gate it
preserved the final hidden state, all logits, and token 2167 bit-for-bit.  Warm
output processing fell to approximately 6.7~ms from roughly 1.1--1.5 seconds.

Within the adaptive candidate, the persistent implementation reproduced every
token ID and every step-logit hash from the earlier subprocess implementation.
It improved the two 17-position continuation passes by 3.14$\times$ and
6.32$\times$.  The resulting speedup is thus an execution improvement, not a
change introduced by the vocabulary calculation.

best stable tail latency.  A four-pass, 24-position validation was then run
with the same adaptive pool.  Routes, final hidden arrays, logits, and token IDs
were identical in all four passes.  The first pass retained cold/warm-up
effects; the three post-warm-up continuation results were:

\subsection{Parallel-expert falsification}

Calculating the four active experts concurrently produced an attractive
isolated BOS result: the exact warm evaluation fell from 0.448 to 0.244 seconds
while preserving the unrestricted final state and logits.  It did not transfer
to sustained generation.  The two 17-position passes fell to 1.7735 and 2.2655
tokens/s despite remaining bit-exact to the serial candidate.  CPU and memory-
bandwidth contention dominated, so sustained parallel-expert execution is
\texttt{STOPPED}.  The isolated micro-result is not used as generation evidence.

\subsection{Quality limitation and next gates}

The adaptive and unrestricted paths shared the first six response-side tokens,
including ``We need to'', then diverged as expected for different router
eligibility.  The minimal prompt ``Hi'' is not a meaningful semantic benchmark;
both resulting short continuations were unsuitable as broad quality evidence.
Consequently the result is \texttt{ADVANCE\_BROADER\_QUALITY\_GATE}, not
\texttt{PROMOTED}.

The next required experiment is a frozen, blinded set of representative
reasoning, extraction, writing, arithmetic, and business prompts.  It must
compare task correctness and response quality against the unrestricted 120B
reference while reporting TTFT, cold activation, warm tokens/s, p50/p95, memory,
and SD traffic.  Only after that gate passes may the pool be called usable.  The
largest remaining warm cost is the native 36-layer MoE calculation, followed by
attention.  Future performance work should test fused packed kernels or a
measured CPU/Metal division under the same frozen quality boundary; it must not
weaken that boundary merely to approach the 30--50 tokens/s research target.

\subsection{Exact semantic prefill with rehydrated bounded generation}

The first held-out arithmetic prompt exposed the limitation of constraining the
entire sequence.  The all-constrained candidate changed ``23'' to ``2?'' in its
analysis and did not reach the correct result within 33 response positions.
This failure was retained.  Exact unrestricted profiling also showed why a
single 10~GiB pool cannot simply preserve the complete prompt route: the
15-position prompt touched 1,005 distinct layer/expert addresses representing
12.405~GiB of original raw expert data.

The runtime boundary was therefore changed, not the acceptance criterion.  All
prompt positions use the unrestricted router and exact selected experts.  At
the prompt/response boundary, AION rehydrates a request-derived 10~GiB pool;
only subsequent autoregressive routing is constrained.  The arithmetic pool
was frozen from the first nine exact prompt positions before its candidate run.

For ``What is 17 multiplied by 23?'', both candidate prompt passes matched the
unrestricted reference token IDs, final hidden arrays, and logits bit-for-bit
across all 15 positions.  Both candidate continuations were internally
bit-for-bit repeatable and produced the correct statement
``17*23 = 391''.  The two 33-position continuations achieved 3.0707 and 2.7253
tokens/s, compared with 0.07213 and 0.07207 tokens/s in the matched unrestricted
reference.  The paired speedups were 42.571$\times$ and 37.813$\times$.
After rehydration, total expert lookup/load time across each 33-position
continuation was only 12.6~ms and 19.1~ms.

This result carries a substantial latency cost.  Initial pool activation took
113.6 seconds and the post-prompt rehydration took 61.6 seconds per pass,
including 5.58~GB of compressed SD reads.  It is therefore a sustained-response
and narrow-quality breakthrough, not an interactive TTFT result.  The correct
next systems experiment is to construct or restore the response working set
incrementally while exact prefill is executing, overlapping its SD work with
neural computation and never allowing it to compete with demand reads.

The narrow arithmetic gate status is
\texttt{PASSED\_NARROW\_ARITHMETIC}; its canonical SHA-256 is
\texttt{ca807decf327196d3fd1ece56012fc5fc3fc3c1a26701b4c5dd94885084cccdc}
and its identical local/SD stored-file SHA-256 is
\texttt{799e66834c4a724ac26f9ab49bf706cbda2dd7d25c27133c1ef14012793329e6}.
The claim remains narrow until the frozen explanation, extraction, and business
diagnosis families pass.

\subsection{Protected workbench and elimination of boundary repair}

The 61.6-second repair was not a necessary property of the model.  It was caused
by ordinary LRU admission: exact prompt misses displaced experts that had
already been loaded for response generation.  A protected-pool store was added.
Pool members are pinned; exact experts outside the pool are still retrieved,
verified and calculated, but remain transient and cannot evict the workbench.

The protected 10~GiB rerun preserved every token, hidden-state hash and logit
hash from the previously correct candidate.  Boundary repair fell to 0.575 and
0.315~ms, with zero repair faults, reads, or evictions.  The two continuation
rates increased to 3.8144 and 3.1990 tokens/s.  The key result is architectural:
exact prompt execution and a stable response working set can coexist inside the
same bounded process without destructive cache interference.

An incremental-admission variant attempted to eliminate the separate initial
activation by retaining useful pool experts as exact prefill requested them.
It was exact and correct, and the first boundary needed only 26 remaining
experts (330~MB compressed, 4.16 seconds).  Cold first-response readiness,
however, remained 161.6 seconds, essentially equal to the protected-preload
condition, because the same unique SD bytes still had to be delivered.  It is
retained as a useful warm-request mechanism, not promoted as a cold-TTFT win.

\subsection{Extraction-family falsification and exact exception halo}

Transfer to a frozen precision-extraction prompt exposed an important boundary.
The prompt was ``Extract the invoice number and total from: Invoice A-104,
total EUR 287.50.''  Its unrestricted 48-position control repeated bit-for-bit
across two passes.  Independently built 8 and 10~GiB constrained pools also
repeated exactly within their respective candidates and ran rapidly, but both
corrupted the decimal amount and entered repetition.  The 8~GiB continuation
reached 5.7062 and 7.9151 tokens/s; the 10~GiB continuation reached 3.0925 and
3.2640 tokens/s.  Neither emitted the frozen required pair A-104 and 287.50,
so both are \texttt{NOT\_PROMOTED}.  Determinism is not semantic correctness,
and the arithmetic-specific 8~GiB result must not be generalised.

This failure motivated an exact design.  The full 128-expert router now remains
unrestricted.  A hash-bound core is protected in memory, while every winning
expert outside that core is retrieved exactly from the verified SD warehouse.
With no room outside an 8~GiB core, misses were transient.  This matched the
unrestricted control at every token, route, hidden-state hash and logit hash,
but only 45 of 792 response layer-routes were wholly inside the core and speed
was only 0.07980 and 0.08027 tokens/s.

A separate ordinary LRU \emph{exception halo} was then placed around the
protected core.  The halo may retain recurring unrestricted winners but cannot
evict the core.  No routing eligibility, gates, weights, or neural arithmetic
are changed.

frontier rather than a second major breakthrough.

The promoted result is the \emph{exact protected-core plus adaptive-exception-
halo mechanism}.  It proves that a bounded portion of ordinary Mac memory can
serve as a reusable loading dock around the SD warehouse while preserving the
unrestricted 120B computation.  It does not establish 30 tokens/s, broad prompt
quality, or full model residency.  At approximately 0.103 tokens/s, expert
movement remains the dominant gap; the next justified work is per-layer halo

\subsection{Native route and in-memory host-flow gates}

Three narrow experiments separated resident neural arithmetic from host
orchestration.  First, one real four-expert route was calculated as a single
GGML Metal graph.  The CPU reference required 0.6928~ms at p50, whereas the
warm fused Metal graph required 1.9372~ms.  Metal was therefore 2.80$\times$
slower.  Its relative $L_2$ error was 0.00749 and its output was not bitwise
equal to CPU.  The candidate is \texttt{NOT\_PROMOTED}.  This falsifies the
available single-token fused Metal path; it does not falsify a future native
MXFP4 Metal kernel with a materially different implementation.

Second, the exact CPU GGML graph was retained and its leaf pointers were
updated between calls.  Output remained bit-for-bit identical, but median wall
time improved only from 0.7116 to 0.6996~ms, or 1.71\%, below the declared
10\% promotion gate.  Graph construction is therefore not a material resident
bottleneck and this mechanism is also \texttt{NOT\_PROMOTED}.

Third, the existing exact native attention, router, MoE and vocabulary stages
were connected through in-memory arrays rather than writing and rereading a
hidden-state file at every layer.  A paired resident BOS position-zero control
fell from 0.40756~s to 0.06531~s on the warm pass, a 6.240$\times$ speedup.
All 36 expert routes, the final hidden-state hash, the complete logit hash and
token 2167 matched exactly.  The mechanism is therefore promoted as
\texttt{PROMOTE\_EXACT\_RESIDENT\_FLOW}.

The 0.06531~s measurement is not a sustained-generation claim.  A genuine
two-token test used changing hidden state, per-layer KV history and changing
routes.  It repeated bit-for-bit across two passes and produced tokens 2167
and 679, but the warm second token still required 16.080~s with the declared
3~GiB cache.  Thus the host-file bottleneck is now removed when weights are
resident, while unrestricted SD misses remain dominant when they are not.

The bound summary has canonical SHA-256
\texttt{25768d87a531e5c803a6869a52f7be6c626af498fa4a00d42f513e4d7cdd0e3}
and identical local/SD file SHA-256
\texttt{62b33c5b82114372c1e9d289e41761a3af38ac8bd61e550f0236c22de7c1552e}.
The next justified scale test is the same exact in-memory flow combined with
the promoted 6+4~GiB protected-core/exception-halo policy.  It must preserve
every token and step-logit hash and must not relabel position-zero resident
execution as generated tokens per second.

That scale test has now completed.  Across the same 26-position extraction
prompt and 22 generated positions, the in-memory 6+4~GiB candidate produced
0.10313 and 0.10181 token/s.  The earlier file-flow candidate produced 0.10282
and 0.10345 token/s.  The paired changes were therefore +0.30\% and -1.59\%:
no replicated speed improvement.  Every route, token, final hidden-state hash
and step-logit hash nevertheless matched both the file-flow candidate and the
separately frozen unrestricted control on all 48 positions of both passes.

The scale decision is
\texttt{NOT\_PROMOTED\_FOR\_SD\_BOUND\_GENERATION}.  The in-memory flow remains
valuable for resident execution, but it does not reduce the 2,508--2,584
expert faults or 31.8--32.8~GB of compressed traffic observed per complete
pass.  The scale summary has canonical SHA-256
\texttt{2ae716234c238aca912dd6bbba766975bcf008521968959c35a54c4c5cb4b78e}
and identical local/SD file SHA-256
\texttt{371f6ac87cc8de68653a4c003e1e6d2eb386e9b859246fd7dd53728511f2b653}.

\subsection{Route-local SD layout falsification}

A bounded physical-layout experiment tested whether the six discontiguous
component reads per expert were responsible for the remaining delay.  A
402,624,694-byte layer-0 micropack copied the existing verified compressed
frames without changing a single encoded or decoded byte and placed each
selected expert's six components next to one another.  The frozen top-32 set
contained 15 complete four-expert routes.  macOS uncached I/O was requested and
the ABBA order was balanced across the routes.

The layout reduced physical read calls from 24 to four per route, but did not
improve time.  Scattered p50/p95 latency was 106.530/113.041~ms, compared with
109.198/115.183~ms for the expert-local pack, a median speedup of only
0.976$\times$.  Every decoded raw component remained hash-exact.  The decision
is \texttt{NOT\_PROMOTED}: seek count at this granularity is not the dominant
cost on the present SD card, and a full duplicate expert-local warehouse must
not be built.

The gate has canonical SHA-256
\texttt{6536c8a70c6d5b20a8ba11bb4b9c10faf15755c6b26849eaae73b68e076c71ba}
and identical local/SD file SHA-256
\texttt{80728464f191e288ddffdf023e40656fb14c5bb5d5261ac332af1dc66b30ccef}.
The next narrow experiment must separate the remaining compressed read,
integrity-hash, zstd decode, allocation and Python-copy costs and test direct
decompression into reusable aligned buffers before any full-runtime change.

The reusable-buffer follow-up remained exact but missed its declared gate.  On
one real six-component expert, the existing copied decode path required
22.871~ms p50.  Removing the encoded-source copy reduced this to 21.761~ms,
and reusing all six decode targets reduced it to 20.996~ms.  The maximum median
gain was 8.93\%, below the predeclared 10\% threshold.  All decoded component
hashes remained exact.  The decision is \texttt{NOT\_PROMOTED}; the additional
buffer ownership and lifetime complexity is not justified while physical SD
traffic dominates.  Canonical SHA-256 is
\texttt{3c2fa7ecf29f4cd902efbce220d7bd67f3bffab78e2ff8f18a84d2f03ef69000},
with identical local/SD file SHA-256
\texttt{1f5c7746846f076880df60ed486661f469e947b565b02dffcdcfbd52303dc86e}.
